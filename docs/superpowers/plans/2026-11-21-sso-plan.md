# SSO for staff: sign in with a PSU Google account

Status: **proposed, not approved** (21 Nov 2026). Changes login, so nothing is built until the
owner approves this plan. Owner request, 21 Nov 2026: "we might need to migrate this to Supabase
Auth for SSO!" and "SSO pa naman habol ko".

## Goal and done-when

Staff sign in to `/admin` with their `@psu.palawan.edu.ph` Google account. Payload keeps accounts,
roles, disabling and the publish rules exactly as they are; Supabase Auth only proves who the
person is.

Done when, on the Preview:

1. An invited staff member clicks "Sign in with Google" and lands in the admin with their role.
2. An unknown PSU account gets "Your request was sent" and appears under Access requests; it
   can read and change nothing.
3. A non-PSU account, an unverified email and a disabled account are refused with a clear message.
4. The super-admin can still sign in with email and password.
5. Disabling an account in the admin blocks that person on their next request, even though their
   Supabase session has not expired.

Every case except the real Google screen has an automated test.

## What was read (21 Nov 2026)

- Payload custom strategies: `auth.strategies` on a collection; `authenticate({ headers, payload,
  canSetHeaders, req })` returns `{ user, responseHeaders? }`
  (https://payloadcms.com/docs/v3/authentication/custom-strategies.md). The installed Payload
  3.90.2 types include `AuthStrategy`, `strategies?` and `disableLocalStrategy`
  (`node_modules/payload/dist/auth/types.d.ts`). The docs do not say whether `beforeLogin` hooks
  run for custom strategies; assume they do not.
- Supabase server auth (Context7, `/supabase/supabase`): verify with `getClaims()`, which checks
  the JWT locally against cached JWKS when the project uses asymmetric signing keys and refreshes
  the session near expiry; `getUser()` is the only way to detect a session revoked server-side;
  `getSession()` must not be trusted for authorization. The PKCE callback calls
  `exchangeCodeForSession(code)` and redirects only to a relative `next`.
- Community pattern "Supabase authenticates, Payload authorizes"
  (https://payloadcms.com/community-help/discord/payload-w-supabase-auth): self-reported, about
  two years old, not endorsed by Payload. Reported pitfalls: rows inserted by a database trigger
  skip Payload hooks; a custom strategy can loop back to the login screen
  (https://payloadcms.com/community-help/discord/cant-get-custom-passport-strategy-to-work).

Not yet checked: whether project `ntzwpcnsjpijfhrgvvin` uses asymmetric JWT signing keys; how
Supabase redirect allow-lists match per-deployment Preview URLs; whether Google's `hd` claim
reaches the Supabase token.

## Design

### Why authorization does not move

Every permission check goes through `getActiveAccount()` (`src/access/activeAccount.ts`), which
reloads `role` and `disabled` from the database on each request, whatever the login method. So a
Supabase-authenticated request gets exactly the same rules as a password one, and disabling an
account takes effect immediately. `getClaims()` not seeing revoked Supabase sessions therefore does
not matter for access; it only matters for sign-out (below).

### Pieces

1. **Sign-in button.** A Payload `admin.components.afterLogin` component: "Sign in with Google".
   It calls `signInWithOAuth({ provider: 'google', options: { redirectTo:
   '<origin>/auth/callback?next=/admin', queryParams: { hd: 'psu.palawan.edu.ph', prompt:
   'select_account' } } })`. `hd` only narrows Google's account picker; it is not a check.
2. **Callback route** `src/app/(frontend)/auth/callback/route.ts`: exchange the code, then
   `getClaims()`. Server checks, in order: email present and verified; email ends exactly with
   `@psu.palawan.edu.ph` (lowercased, no subdomains); a Payload account with that exact email
   exists, is not disabled and has a staff role. Outcomes: success → `/admin`; no account → upsert
   an access request, sign out of Supabase, redirect to the login page with "Your request was
   sent"; disabled or wrong domain → sign out, redirect with the matching message. `next` must be
   a relative path.
3. **Payload strategy** `supabase-sso` added to `Users.auth.strategies`; the local strategy stays.
   It builds a Supabase server client from the request cookies, calls `getClaims()`, repeats the
   domain and email checks, loads the Payload account by email and returns it with
   `collection: 'users'`, or `null`. It never creates accounts or requests. Refreshed cookies go
   out through `responseHeaders` only when `canSetHeaders` is true.
4. **Access requests**, a new collection kept apart from `users`: `email` (unique), `name`,
   `requestedAt`. Read and delete for admins and up; create and update denied through the API (only
   the callback writes it, server-side). "Approve as Editor/Publisher" creates the account through
   the existing account guards with the admin as actor, then deletes the request.
5. **Invite.** The existing "create account" flow. Payload requires a password on create, so an
   invited SSO-only account gets a random 32-byte password generated on the server and never shown.
6. **Sign out.** The account menu signs out of Payload and Supabase together.

### Environment

`NEXT_PUBLIC_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` (public by design; no
service-role key is needed for sign-in), and `SSO_ALLOWED_DOMAIN=psu.palawan.edu.ph`. Set in
Vercel Preview first.

## Tests (written first, failing, then the code)

- Strategy: valid PSU token + active account → that user; wrong domain, look-alike domain
  (`psu.palawan.edu.ph.evil.com`, `evilpsu.palawan.edu.ph`), unverified email, unknown email,
  disabled account, non-staff role, missing or tampered cookie → `null`.
- Callback: open-redirect attempts in `next` are refused; unknown PSU email creates exactly one
  access request on repeated sign-ins; no request is ever created for a non-PSU email.
- Access requests: anonymous and editor API create/read/update are denied; approving as an admin
  creates the account with the chosen role; an admin cannot approve a super-admin.
- Disabling an account blocks a Supabase-authenticated request on the next call.
- Password login for the super-admin still works with the strategy installed.
- Browser test with Supabase mocked at the network edge: button → callback → dashboard, and the
  "request sent" message. The real Google screen is checked by hand on the Preview.

## Risks

- The login loop reported with custom strategies: covered by the browser test.
- Per-deployment Preview URLs vs Supabase's redirect allow-list: check before building; fall back
  to a fixed Preview alias if wildcards do not fit.
- Supabase becomes a second thing to keep running after hand-over: Auth is part of the project
  already used for the database, so no new account or bill.
